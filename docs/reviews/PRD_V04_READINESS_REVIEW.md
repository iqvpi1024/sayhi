## 2. 总结

PRD 已经明确产品定位、语义红线、Micro-MVP 主链路和首年非目标，足以阻止多租户、多 Agent、全连接器和通用图平台等明显扩张。依据为 PRD §1、§6、§24.1、§24.7、§25.3。

PRD 尚不能无裁决地进入第一份正式 SPEC。主要原因不是技术选型缺失，而是核心语义边界仍有冲突：`RelationshipState` 未被纳入或映射到 12 类对象；`Assertion` 内容类型、审查状态与回答状态混用；“五态”实际列出五态并追加 `unknown`；Source 的快速追加与“所有规范写入必须经过 ChangeSet”边界不明；12 对象之外仍出现 `Obligation`、`Snapshot`、`viewpoint` 等词。依据为 PRD §6、§7.2、§8、§8.1、§9.4、§11、§13、§18.2、§22.2、§24.1、§27.3。

| ID | 缺口 | PRD 依据 | 风险 |
|---|---|---|---|
| P-01 | 硬删除没有定义 live data、索引、缓存、导出副本和备份各自的完成时限及失败回执 | §6.13、§12.4 | 可能产生虚假“已删除”承诺 |
| P-02 | 不可变 Revision Ledger 与硬删除仅留最小证明之间缺少去正文/去标识规则 | §7.1、§11、§12.4 | 审计记录可能继续泄露已删语义 |

| P-04 | 用户完整私有导出与“分享和导出时第三方默认脱敏”没有区分 export purpose | §17.5、§21.4 | 可能过度删减用户自有备份，或外发泄漏第三方信息 |

## 11. Micro-MVP 最小化建议

依据 PRD §24.1 和 §26 Case A，Micro-MVP 仍可缩小为一个确定性语义切片：

1. 只用一段固定合成纯文本，不接文件、音视频或第三方规范包。
2. 使用两个预置且无歧义的合成 `Entity`，不做实体发现、合并或拆分。
3. 只提出一个 `contact_state: active -> no_contact` proposal；不做通用关系抽取。
4. 使用明确的 `valid_from` fixture，暂不实现模糊时间解析。
5. 只发布 `RelationshipState` 所需的最小规范变更；对象归属由 `BQ-001` 裁决。
6. Micro Core View 暂按人物卡和关系时间线定义验收；是否加入独立“当前状态”视图由 `IQ-001` 裁决。
7. `trust`、`closeness`、`origin`、`role` 和人格 Hypothesis 只作为禁止变化的断言，不构建推断能力。
8. 撤销只验证整个已发布 ChangeSet；单 proposal 撤销、提醒和 Semantic Diff UI 后置。
9. 用确定性 fixture 驱动“识灵提出候选”，不把模型选择、Prompt 质量或通用 NLP 作为 Micro 通过条件。
10. 增加两个必要失败场景：stale `base_revision` 不得半发布；L2 更新失败不得把旧值冒充最新。

该缩小不删除 PRD 能力，只限制第一条可执行链路的实现面。对应验收见 `docs/testing/MICRO_MVP_ACCEPTANCE.md`。
